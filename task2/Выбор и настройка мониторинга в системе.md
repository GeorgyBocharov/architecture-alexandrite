# Выбор и настройка мониторинга в системе


## Мотивация
В систему критически важно добавить мониторинг: сейчас непонятно, почему теряются заказы: нужно найти происходят ли потери из-за перегрузки Rabbit MQ или из-за ненадежной фиксации факта отправленного сообщения в сервисе. 

Также необходимо фиксировать длительность обработки заказов в системах CRM, MES, Shop

## Выбор подхода к мониторингу

|сервис|подход|причина|
|---|---|---|
Shop|4 signals| на сервис поступают пользовательские запросы, он их сохраняет в базу, нужно понимать время ответа сервера, rps запросов на заказ, загрузку приложения (память + cpu utilization)
CRM| USE | Необходимо понять, справляется ли сервис с обработкой сообщений из MQ, не является ли он узким горлышком
MES | 4 signals + USE | Этот сервис закрывает очень много функционала: расчитывает 3д модели, принимает заказы от партненров, предоставляет API для операторов. Необходимо понимать, справляется ли MES и хватает ли ему ресурсов.

## Метрики по сервисам

### Shop

|метрика|обоснование|
|--|---|
Number of requests (RPS) for internet shop API | понимание сколько заказов получаем от этого канала
Number of HTTP 200 for shop API | % успешных запросов, соответствие SLA
Number of HTTP 500 for shop API | % ошибок, соответствие SLA
Number of connections for shop db instance  | количество запросов к базе, важно понимать, что CRM тоже использует базу напрямую
Memory Utilisation for shop db instance | Загруженность базы
Response time (latency) for shop API | соответствие SLA
CPU % for shop API | здоровье сервиса
Memory Utilisation for shop API | здоровье сервиса, отсутствие утечки памяти

### CRM

|метрика|обоснование|
|--|---|
Number of requests (RPS) for CRM API | количество обращений к сервису
Response time (latency) for CRM API | время обработки 
Rabbit MQ processing rate | скорость обработки консьюмера ивентов
Number of message in flight in RabbitMQ | количество ожидающих обработки сообщений
Number of dead-letter-exchange letters in RabbitMQ | сообщения в DLQ (ошибка обработки)
Memory Utilisation for CRM API | использование памяти в CRM
Response time (latency) for CRM API | длительность ответа по методам (для мониторинга работы менеджеров)
Number of HTTP 200/500 for CRM API  | количество успешных и ошибочных ответов от менеджеров

### MES
|метрика|обоснование|
|--|---|
Number of requests (RPS) for MES API | количество обращений к сервису с тегами запросов от партнеров или операторов
CPU % for MES API | загруженность MES
Memory Utilisation for MES API | память MES
Rabbit MQ processing rate | скорость обработки консьюмера ивентов
Number of message in flight in RabbitMQ | количество ожидающих обработки сообщений
Number of dead-letter-exchange letters in RabbitMQ | сообщения в DLQ (ошибка обработки)

Memory Utilisation for MES db instance | состояние памяти базы MES
Size of MES db instance | размер базы MES

## План действий
1) Поднимаем  отдельный сервер для мониторинга (2 vCPU, 4 ГБ RAM, 50 ГБ HDD/SSD). Так жизнеспособность метрик не будет зависеть от загруженности основного сервера.
2) Настраиваем экспортеры на сервисах, базах и Rabbit MQ:
   1) в приложениях настроить http эндпоинт с метриками и подключить клиентскую библиотеку Prometheus для сохранения метрик
   2) Активировать плагин prometheus для Rabbit (rabbitmq_prometheus)
   3) Устанавливаем postgres_exporter (экспортер Prometheus для Postgres) на сервер с PostgreSQL. Создаем отдельного пользователя для мониторинга.
   4) Добавить в systemd проверку что postgres_exporter поднимается вместе с базой
3) Поднимаем Prometheus:
   1) Скачиваем бинарник prometheus
   2) Создаем конфиг файл с экспортерами, интервалами сбора и правилами алертов
   3) Создаем systemd сервис для работы prometheus
4) Поднимаем Graphana
   1) Разворачиваем также через systemd (graphana server)
   2) Настраиваем graphana на prometheus
   3) Создаем дашборды для наших сервисов + стандартандые дашборды для RabbitMQ и БД

## Аллерты
В прометеусе можно настроить аллерты: для этого ставим пороговые значения на метрики:

1) доля ошибок shop, mes api > 5%
2) rabbit in-flight messages > 10000 - копится большой лаг => консьюмер не справляется
3) p90 latency ответа > 2 sec
4) заполненость бд и s3 > 90%

Скачиваем AllertManager, подключаем его к Prometheus, указываем в нем пороговые значения метрик и каналы нотификаций
